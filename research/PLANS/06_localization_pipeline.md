## 2. PO 键设计

`msgctxt` 必须能唯一定位回二进制里的插槽，且人类可读：

```
olang    olang/<table_id>/<group>/<entry>      例 olang/009c9ea4/00bc4a75/0000
codec    codec/<group>/<sector>/<idx>/<line>   例 codec/1/0/0/0
```

- `msgid` = 英文原文（olang 取 en 槽；CODEC 取 en 语言块，见 03 号 §语言归属）
- `msgstr` = 译文
- `#:` 引用写 `源TSV:行号`，便于回溯
- `#.` 提取注释按来源附加语义：
  - olang 字幕行：`subtitle mode=N pack=AVD0000N slot=N`
  - CODEC：`speaker=0x0e28dce6 voice=v_bri_kaz0010_000_0 t=473..1490`
  - 其余六语言的现有译文一并作为参考注释，译者可对照

拆成多个 `.po`（按 table_id / 按 CODEC 记录段）以便分工，用 `.pot` 作模板。

## 3. 必须逐字保留的内联标记

| 标记 | 出处 | 规模 |
|---|---|---|
| `<I=...>` 按键/图标引用 | olang（01 号 §4） | 需枚举建表 |
| 换行 = **真实 `0x0A`** | olang | 4,289 条（另 181 条含 `0x0D`） |
| `%d` 等格式符 | olang | 需随译文保留 |
| `<R=表示,よみ>` 振假名 | CODEC（03 号） | 188 种 / 330 次 / 270 条记录 |

> 换行**不是**字面 `\n` 两个字符（`_probe_olang4.py` 实证：字面反斜杠-n
> 零命中）。误判源于 `_probe_dump.py` 把真实换行转义后写进 TSV。
> `.po` 导出时要还原成真实换行，导入时同理。

`<R=>` 是日文振假名，中文译本大概率整体去掉；但**去掉是显式决策**，
必须由校验器报出来而不是默默丢失。

## 5. 编译回写链

```
.po ──┬─> olang 序列化器 ─> 重新 XOR 加密 ─> MLG/Text/*.olang     [计划 01 待办 3]
      ├─> CODEC 字节码回写                                        [受阻，见下]
      └─> 码点汇总 ─────> 字库构建器 ─> FONT/0007ccd8.xpr         [计划 05]
```

**olang 侧**：字符串池是偏移寻址（`key[].str_off`），译文变长只需重排池子，
不存在定长槽限制。重算三表偏移与 `group_count`，`table_id` 保持不变。

**CODEC 侧受阻**：台词内嵌在字节码流里，而 `briefing_insn_decode` 的
`case 0x10 / 0x20` 长度规则未反（03 号 §2），重新发射指令有把脚本写跑飞的
风险。两条备选：

1. 先反完那两个 case，再做真回写；
2. 只对 CODEC 走 detour（hook 取字符串处），文本侧仍由 `.po` 统一管理。

> 即便 CODEC 最终走 detour，`.po` 管线也不变——只是后端换一个投递方式。

## 6. 校验器（编译前必须全过）

`pwsf.po_lint` 实现，error 非零退出即阻断编译。括号里是错误码。

- [x] 引用能解析且解得到真实槽位（`ref`）
- [x] **`msgid` 仍与原文逐字符相同（`msgid-drift`）** —— 这条是"引用可以当
      写回地址"的前提；语料重新导出后原文若变了，挂在上面的译文就是过期的
- [x] 内联标记逐字相等：`<I=...>` 取值与数量（`icon`，含未闭合的 `<I=`）、
      `%d` 一类格式符（`format`）
- [x] `<R=>` 振假名不得静默消失（`ruby`，`--allow-ruby-drop` 降级为警告）
- [x] 空串守恒：原文非空的槽位不得变成纯空白（`blank`）；`msgstr` 留空
      表示未翻译，该槽位保持英文
- [x] 控制字符（`control`）：`\0` 会在字符串池里把后面截断
- [x] 同一槽位不得被两条不同译文认领（`conflict`）
- [x] **码点全部落在字库能力内**（`font`）：超过 `cMaxGlyph U+FF5E` 的码点
      无法进转换表；TTF 里没有该字形的会变豆腐块，见 05 号 §9.2
- [x] olang 往返等价 + 写回定位正确 —— 由 `po_import` 在构建后复验：
      重新解密解析，逐槽位比对，**除声明要改的槽位外必须逐字节相同**
- [ ] 行号/行数守恒：字幕组的 entry 键必须仍是 `0..a1[31]-1` 连续区间
      （02 号 §6.2）。当前写回不增删 entry，区间天然守恒，等真正要动
      字幕结构时再补断言；CODEC 的 `0x6d args[6]` 行号随 CODEC 回写一起做
- 换行数变化只报**警告**（`line-count`）：重新断行往往是有意的，
  但游戏不自动折行，超长会被裁掉，所以必须提示

> 每条检查都有对应的失败用例，见 `_probe_po4.py`：15 个缺陷各自只触发自己的
> 错误码，另有 1 个正确译文用例必须一声不响。没被人看过失败的校验器等于
> `return []`。

## 8. 导出实测（已完成）

```
olang  2,781 个英文槽 → 1,513 条（按 msgid 合并，重复率 46%）→ 4 个文件
codec  4,839 个英文槽 → 4,746 条（重复率 2%）              → 12 个文件
合计   6,259 条，覆盖 7,620 个槽位
```

- **EXLANG 不是语料来源**：其英文槽全空（实测 0 条非空），只带葡语。
- 每文件约 400 条，可一人一文件并行。索引见 `src/MANIFEST.tsv`，
  译者须知见 `src/README.md`。
- 校验（`_probe_po2.py`）：解析全部 17 个文件，把每条 `#:` 引用解回游戏数据，
  确认 **msgid 与原文逐字符一致**，且 7,620 个非空槽位**全部覆盖**。

> 条数修正：本节原记 olang 1,514 条 / 合计 6,260 条，是把 `.pot` 的
> 空 `msgid` 文件头当成了一条语料。`MANIFEST.tsv` 各行相加与
> `po_lint` 的计数都是 **1,513 / 6,259**（`pwsf.po.iter_entries` 跳过文件头），
> 以后者为准。

> 导出过程中校验器抓到一个真实缺陷：语料里有 181 条含裸 `0x0D`，
> 而注释写入只按 `\n` 切行，导致产生了未加 `#.` 前缀的物理行、PO 语法失效。
> 已改为按 `splitlines()` 切分。

### 8.1 提取必须读原始文件，不能读已安装的构建产物

第一版导出把 `009c9ea4` 中 8 条**我们自己的 PoC 译文当成英文原文**导了出来。
根因：`_poc_text_cn.py --install` 就地覆盖了游戏目录里的 `009c9ea4.olang`，
而导出器读的正是游戏目录的实时文件。

**校验器当时没报错**，因为它读的是同一份被改过的文件——两边一致，
检查自然通过。这类「源与校验共用同一个被污染输入」的盲区必须靠设计规避，
而不是靠更严的断言。

修法：`config.pristine(path)` 在存在 `*.orig` 备份时返回备份，
所有**提取**路径（`po_export` / `subtitle` / `_probe_po1` / `_probe_po2`）
一律经它读取。`name_hash` 在第一个 `.` 处截断，所以
`009c9ea4.olang.orig` 与 `009c9ea4` 的密钥相同，备份可直接解密。

另外 `po_export` 现在会在检测到已安装构建时显式打印一行提示，
让「游戏里装着构建产物」这个状态不再隐身。

## 9. 管线闭环实测

命令与产物：

```powershell
python -m pwsf.po_import --install   # 一条龙：校验 + 编译 + 复验 + 安装
python -m pwsf.install --restore     # 还原

python -m pwsf.po_lint             # 分步：6,259 条 / 7,620 引用，全部校验
python -m pwsf.po_import           # 分步：-> research/BUILD/*.olang + *.xpr + MANIFEST.tsv
python -m pwsf.install             # 分步：只报状态，不写任何东西
python -m pwsf.install --install    # 分步：安装已编译好的产物
```

`--install` 把清单交给 `pwsf.install`，所以拒绝路径完全一致——
认不出来的现场文件照样不写。

用 PoC 那 8 条译文作**验收标尺**（它们现在就躺在 `src/olang/olang_03.po` 里，
是普通译文），`_probe_po3.py` 的结果：

```
lint     6,259 条 / 7,620 引用 / 7 条已译 -> 11 个 olang 槽 / 57 个码点
重建     009c9ea4.olang  11 槽改写  395,505 字节（原 398,374，池去重后更小）
标尺     8 个 PoC 槽位逐字符等于实机验证过的文本
隔离     11,742 个字符串中恰好 11 个与原文不同，且全在 en 键
合并     比 PoC 多出 3 个槽位（同一句英文在 group 0x596F30 的三处重复）
字体     643 -> 675 字形（+32），原有 642 个映射一个没动，仍剩 50 行
```

**多出来的 3 个槽位是特性不是缺陷**：导出按 msgid 合并，
"Return to the title menu?" 在 `0x596F30` 还有三处，一条译文自动覆盖全部，
这正是合并导出的收益（短词全局一致）。

> 一条独立旁证：本管线产出的 `0007ccd8.xpr` 与 **PoC 实机验证过的那份字体
> 逐字节相同**（`install` 报 `unchanged / 已安装`）。同样的码点集合、同样的
> 装箱顺序 → 同样的字节，说明字体构建是确定性的，且新链路没有引入偏差。
> olang 侧覆盖面比 PoC 更大（11 槽 vs 8 槽），实机复看待跑一次。

安装侧的状态机（含各种拒绝路径）由 `_probe_po5.py` 在**合成游戏目录**上逐态
走过：首装会备份、重复安装不动备份、还原可回原、
备份不是原文或无备份而现场文件陌生时拒绝写入（`--force` 才能越过）。
理由是 `*.orig` 是全部提取路径的英文来源（§8.1），备份错了会污染语料。
